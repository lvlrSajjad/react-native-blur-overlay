# Live Backdrop Blur on Android for a React Native Fabric View Library

## TL;DR
- **There is no fully-general, shippable way to get iOS-style *live* backdrop blur for an arbitrary in-window Fabric view on today's Android install base without either (a) a BlurTarget-style per-frame RenderNode re-recording that forces users to wrap the blurred content, or (b) waiting for the true system primitive `RenderNode.setBackdropRenderEffect`, which is public only from Android 17 QPR2 / SDK 37.2 (targeted stable ~December 2026, ~0% install base).** Your compositor-level dream API (`SurfaceControl.Transaction#setBackgroundBlurRadius`) is `@hide` in AOSP and therefore disqualified by your constraint #1.
- **The recommended shippable path is a per-frame RenderNode re-record ("BlurTarget") pipeline modeled on Dimezis BlurView v3 / Haze, running the blur on the system RenderThread via `RenderEffect` on API 31+, with your existing snapshot as the graceful fallback below 31.** This is the only approach that is public-API, permission-free, in-window, and actually live while content scrolls. Its unavoidable cost is the one you wanted to avoid: the content to be blurred must live in a target subtree that excludes the overlay.
- **Adopt a tiered strategy:** SDK 37.2+ → `setBackdropRenderEffect` (no restructure); API 31–36 → RenderNode+RenderEffect BlurTarget (restructure, live, ~free capture); API 24–30 → your current downscaled snapshot (still), optionally re-blurred at 15–20 fps. Treat temporal decoupling and aggressive downscale as quality/perf knobs, not as ways to escape the restructure requirement.

## Key Findings

### Your prior knowledge, checked
- **`RenderEffect.createBlurEffect` (API 31+) blurs a view's OWN content, not what's behind it — VERIFIED.** `View.setRenderEffect()` "will apply a visual effect to the results of the View before it is drawn"; it operates on the view's own layer, not the backdrop. Correct as stated.
- **`Window.setBackgroundBlurRadius` / blur-behind (API 31+) is public, live, system-side, but window-scoped and gated — VERIFIED.** It is a public method on `android.view.Window` (ApiSince=31), requires a translucent window, and requires `WindowManager.isCrossWindowBlurEnabled()` which is false under battery saver, on GPUs/SurfaceFlinger without support, and when the developer option is off. It only blurs what's behind a *window*, so it applies to Dialog-hosted overlays, not an in-window Fabric view. Correct as stated.
- **`RenderNode.setBackdropRenderEffect` is the correct primitive and lands in Android 17 QPR2 / SDK 37.2 — VERIFIED.** It appears in the official SDK 37.2 method-additions diff for both `android.graphics.RenderNode` and `android.view.View`. Android 17 stable shipped June 16, 2026 as API level 37; QPR2 (the minor SDK release, SDK 37.2) is in beta and targeted for a stable December 2026 release. So install base is effectively zero today and will be tiny for a long time. Correct — verified.
- **Dimezis BlurView v3 re-records a BlurTarget subtree into a RenderNode every frame, applies a RenderEffect, runs on the RenderThread on API 31+, is JitPack-distributed, and requires a BlurTarget that excludes the blur view — VERIFIED.** README: "On API 31+ the blur is done on the system Render Thread… BlurView and Haze… leverage hardware acceleration for View snapshotting and have near zero overhead of snapshotting." v3 migration: "you have to wrap the content you want to blur into a BlurTarget… The BlurTarget may not contain a BlurView that targets the same BlurTarget." License is Apache-2.0 (Copyright 2025 Dmytro Saviuk). Correct as stated.
- **expo-blur uses the Dimezis approach, was experimental for years over performance, and cannot cross React Native Modal boundaries — VERIFIED.** expo/expo issue #44165 (opened Mar 2026): "BlurTargetView cannot reference content outside the Modal because Modal renders in a separate native window." Correct as stated.
- **MediaProjection — correctly disqualified** (consent dialog + persistent notification; violates constraint #2).
- **Your Java Stack Blur baseline (~43ms on a 1080×1920 frame on desktop JVM)** is consistent with the general finding that CPU Gaussian on full-res frames is far over-budget; this is exactly why the snapshot/downsample exists.

### Question 1 — `SurfaceControl.Transaction#setBackgroundBlurRadius`: is it public?
**NO — it is `@hide`. Close this off. (VERIFIED against AOSP master.)** In `frameworks/base/core/java/android/view/SurfaceControl.java`, the method is annotated `@hide`:
```java
/** @hide */
public Transaction setBackgroundBlurRadius(SurfaceControl sc, int radius) { … }
```
The native side (`SurfaceComposerClient::Transaction::setBackgroundBlurRadius`) exists and is what SurfaceFlinger uses for window blurs, but the Java method is not part of the public SDK. Reaching it requires reflection into a non-SDK interface, which violates hard constraint #1 (Play risk, breaks for a dependency in other people's apps). The EffectLayer builder path that would let you *create* a blur layer is also `@hide`. **This is the cheapest-possible win in theory and it is not available to a public-SDK app.** Dead end.

### Question 2 — `RenderNode.setBackdropRenderEffect`: SDK level and applicability
**Public from SDK 37.2 (Android 17 QPR2). VERIFIED.** It is the exact API Google itself uses for backdrop blur; the AOSP HWUI backend (`libs/hwui/pipeline/skia/BackdropFilterDrawable.cpp` and `RenderNode.cpp`) derives the backdrop snapshot area from the RenderNode bounds and comments: *"always damageSelf when filtering backdrop content, or else the BackdropFilterDrawable will get a wrong snapshot of previous content."*

Can an app apply it to an ordinary View's RenderNode? **Partially — with a caveat.** The primitive operates on a `RenderNode`, and the official `android/compose-samples` PR #1710 (riggaroo, Sept 2026) demonstrates a `Modifier.backdropBlur{}` built directly on `RenderNode.setBackdropRenderEffect`, described as "using underlying Android SDK 37 primitive." Haze's PR #1323 wires it via a "cached reflective bridge" only to avoid a compile-SDK 37.2 requirement, and Haze exposes it only as an experimental, off-by-default `HazeFeatureFlags.isPlatformBackdropEnabled`. It composites the backdrop that is drawn *behind that RenderNode in the same window/display-list*, so it works for a normal view provided the blurred content is drawn earlier in the same window — exactly your in-window Fabric scenario. **Verified that it exists and is public at 37.2; uncertain in the sense that no production RN integration exists yet and Google's own Compose support (`Modifier.backdropBlur{}`) is still "coming soon."**

Notably, **Haze measured the native path as SLOWER on CPU than its source-based path**: on a Pixel 8a at 60 Hz, "native Backdrop had 23–46% higher CPU frame P90 than Sources in the tested single-surface Glass workloads" (two order-reversed passes at Quality, 8 iterations per method per pass, 160 iterations total). So even the "correct" future API is not automatically a performance win — it re-filters window pixels each draw rather than reusing processed output.

### Question 3 — What does per-frame RenderNode re-recording actually cost in an RN long-list-behind-a-panel scenario?
**Nobody has published a measurement for exactly your case (RN Fabric, ~400dp panel over a scrolling FlatList). The closest published numbers are Haze's Compose benchmarks. (Verified numbers below; RN-specific = uncertain / unmeasured.)**

Haze's scenario benchmarks were run with **16 iterations on a Pixel 6 on the latest Android**, reporting **P90 frame duration in ms**. Key verified facts:
- The snapshot/re-record itself is cheap because it uses hardware-accelerated RenderNode recording on the RenderThread — Haze and Dimezis both claim "near zero overhead of snapshotting."
- Haze's own guidance stresses that **cost scales with (a) the area covered by the effect, (b) the number of effects/RenderNodes, and (c) whether content behind is changing.** Scrolling content forces fresh capture every frame ("Scrolling or animated backgrounds need fresh input").
- **`inputScale = 0.5` reduced Haze's cost by 5–20% on Pixel 6** — direct evidence that downscaling the captured backdrop is a real, measured win (relevant to your "aggressive downscale" seed).
- On a Pixel 8a, quality-mode tuning of Glass left ~5 ms of frame-deadline headroom at P90 in Balanced vs ~1.7 ms in Quality (60 Hz, changing background, 8 iterations) — i.e. the blur pass alone can eat most of a 16.6 ms budget at high quality on mid-range hardware.

The honest read: **on a Pixel-6-class device the re-record + RenderEffect blur can hold 60fps for a single moderate panel, but headroom is thin and disappears with larger blur areas, higher quality, or 120Hz (8.3ms budget).** For RN specifically the extra risk is that Fabric's view hierarchy and the JS/shadow-tree churn add their own frame cost; you must measure on-device. (Note: I could not extract the exact per-scenario enabled-vs-disabled ms cells from Haze's `benchmark-results` page — it's JS-rendered and did not yield the individual table values; those specific cells remain unverified.)

### Question 4 — AttachedSurfaceControl / SurfaceControlViewHost / HardwareBuffer path to the backdrop buffer without MediaProjection?
**No usable public path. (Verified for the blur-relevant methods.)** `getRootSurfaceControl()` returns an `AttachedSurfaceControl` (ApiSince=31), but it is "just the interface to the windowing-system object that contains the entire view hierarchy" — it does not expose a readable backdrop buffer, and the only blur lever on `SurfaceControl.Transaction` (`setBackgroundBlurRadius`) is `@hide`. `SurfaceControlViewHost` is for *embedding* another app's hierarchy (SurfacePackage), not for reading back what's beneath your view. `HardwareBuffer` + `HardwareRenderer` can render a RenderNode into a buffer (that's the accelerated bitmap-blur path), but it does not give you the *backdrop* pixels — you still have to draw the content yourself into a RenderNode, which is exactly the BlurTarget re-record. **There is no zero-capture, public-API route to the composited backdrop below SDK 37.2.**

### Question 5 — React Native renderer or @shopify/react-native-skia BackdropFilter?
**No. Skia's BackdropFilter only blurs pixels drawn inside the same Skia `Canvas`; it cannot blur native views (a scrolling FlatList) that live outside the canvas. (VERIFIED — from the maintainer.)** react-native-skia maintainer William Candillon, in discussion #3223: "it won't work with scrollable content outside the Skia canvas unfortunately… Unfortunately if you want to apply it to native views I wouldn't recommend to use Skia for this, especially for Android." The RN renderer itself exposes no backdrop-capture primitive. Skia is only viable if you also draw the background *inside* the Canvas — the same "same-surface" constraint as Flutter. Dead end for your use case.

### Question 6 — How Flutter's BackdropFilter works, and is any of it reachable for RN?
**Flutter's BackdropFilter works because Flutter owns the whole surface: the engine (Skia or Impeller) captures the current render target / save-layer within its own single surface, applies the ImageFilter, and composites. It is live because Flutter re-renders every frame anyway. (VERIFIED.)** This is fundamentally an in-engine, same-surface technique. Flutter issue #149368 confirms the cost model: "Despite covering only a small region of the screen, for Impeller we will process and restore the entire screen to implement the backdrop." Impeller has repeatedly had backdrop-blur perf regressions (#138615 janky scrolling, #126353 degradation with multiple filters).

**Reachable for RN? No — not for native views.** RN renders to the Android View hierarchy (HWUI), not a single engine-owned surface. The only analog available to a View-based renderer is precisely the RenderNode re-record (which is Android's own in-HWUI equivalent of the save-layer capture). So the "Flutter technique" for RN reduces back to the BlurTarget approach. The only way to get Flutter-style behavior in RN is to draw the background inside a Skia Canvas (Question 5), which defeats "don't restructure the app tree."

### Question 7 — AGSL / Vulkan dual-Kawase vs RenderEffect's Gaussian: better quality-per-ms?
**Yes, dual-Kawase is dramatically cheaper per-ms at large radii — but it is almost certainly not worth it for you, because `RenderEffect` already runs the Gaussian on the RenderThread/GPU for free and a custom shader means capturing pixels you can't easily get. (Benchmarks verified; applicability uncertain/negative.)** Representative numbers (Blender compositor PR #152155, RTX 3080 Ti, 4K, GPU): Gaussian at radius 20/200/1000 = 5.5 / 28.0 / 108.3 ms; dual-Kawase = 0.8 / 0.9 / 0.9 ms — i.e. dual-Kawase is near-constant-cost regardless of radius while Gaussian scales with radius. Marius Bjørge's ARM SIGGRAPH 2015 talk "Bandwidth-Efficient Rendering" describes the dual-filter (down/upsample) Kawase blur — "sampling four corners at increasing distance" — and ARM's own Mali-T760 MP8 (Samsung Galaxy S6) tests found "the Dual Blur algorithm has the fastest speed and the best performance"; Intel's 2014 blog "An investigation of fast real-time GPU-based image blur algorithms" (software.intel.com) corroborates that Kawase closely approximates Gaussian at a fraction of the bandwidth on mobile GPUs.

The catch: `RenderEffect.createBlurEffect` is a black-box Gaussian applied by HWUI at effectively no marginal cost to you, on pixels HWUI already has. To run your own AGSL (API 33+) or Vulkan dual-Kawase you would need the backdrop as a texture you control — which on <37.2 means the same capture problem, plus you lose HWUI's free RenderThread integration. **Recommendation: use `RenderEffect`'s Gaussian; only consider AGSL dual-Kawase if you're already capturing to a HardwareBuffer and profiling shows the Gaussian is your bottleneck at large radii (which downscaling fixes more cheaply).**

### Question 8 — Prior art: Compose Haze and anything newer
- **Haze (chrisbanes/haze) — Apache-2.0, on Maven Central (`dev.chrisbanes.haze:haze`, current 2.x). VERIFIED.** It is Compose-Multiplatform-only (depends on `org.jetbrains.compose.ui`), so **not directly usable in a Fabric View library** — but it is the reference implementation and its architecture/measurements are the best available. Newer than the source-based path, it added an experimental native `setBackdropRenderEffect` backend (Haze 2.0.0-beta03) behind a flag, and measured it as CPU-slower than the source path (see Q2).
- **Haze pre-API-31 fallback — VERIFIED.** Haze supports "all versions of Android, using RenderScript underneath." On Android 11 and below blur is *disabled by default* (`blurEnabled` opt-in) and uses `ScriptIntrinsicBlur` (radius clamped 0–25 px), processed on a background thread, which "may appear laggy." This mirrors your own <31 snapshot fallback.
- **Dimezis BlurView v3 — Apache-2.0, JitPack-only (`com.github.Dimezis:BlurView:version-3.2.0`). VERIFIED.** Canonical distribution is JitPack, which is exactly the friction you want to avoid (constraint #5). **A Maven Central re-publication exists: `com.huanli233.blurview:blurview:3.0.0`, Apache-2.0** — but it lags upstream (3.0.0 vs 3.2.0), its POM still points at the Dimezis repo, and it is best treated as an unofficial one-off republish, not a maintained fork. Relying on it is a supply-chain risk.
- **Compose 1.13's new progressive-blur modifier** blurs a composable's *own* content (RenderEffect, H+V shader passes), not the backdrop — not a backdrop solution.

### The `@react-native-community/blur` state
For completeness: the community package is at **4.4.1, published August 29, 2024 by Thibault Malbranche (titozzz, of Brigad), MIT-licensed**, and largely static. Its original README billed it as "500px-android-blur on Android" (RenderScript, with the "BlurView cannot be a child of the view being blurred" limitation); current docs (DeepWiki) indicate it now wraps the Dimezis BlurView library via JitPack. Either way it carries the same restructure constraint.

## Recommendation

**Build a tiered "live backdrop" pipeline whose primary tier (API 31–36) is a per-frame RenderNode re-record of a BlurTarget subtree with a `RenderEffect` Gaussian applied on the RenderThread, downscaled ~0.5, re-captured only when the backdrop actually changes; with `RenderNode.setBackdropRenderEffect` as a no-restructure fast path on SDK 37.2+, and your current snapshot (optionally re-blurred at 15–20fps) as the graceful floor on API 24–30.**

Concretely:
1. **SDK ≥ 37.2:** use `RenderNode.setBackdropRenderEffect` — no app-tree restructure needed, this is the real primitive. Gate on `Build.VERSION.SDK_INT_FULL` (note the Robolectric/SDK_INT_FULL quirk: 37.2 = 3_700_002).
2. **API 31–36:** BlurTarget re-record + `RenderEffect.createBlurEffect`, capture on RenderThread, apply blur there, draw as the overlay's background. Only invalidate/recapture when the target subtree reports a draw (Dimezis's "updates only when needed"). Downscale the captured RenderNode.
3. **API 24–30:** keep today's downscaled snapshot; optionally add a 15–20fps re-blur timer so a scrolling backdrop at least updates coarsely (RenderScript or your Stack Blur on a background thread, accepting 1–2 frames latency).
4. **Hybrid bonus:** when the overlay is genuinely full-screen AND `isCrossWindowBlurEnabled()` is true AND you can host it in a Dialog window, offer an opt-in `Window` blur-behind mode for free system-side live blur.

**Strongest honest argument AGAINST this recommendation:** *It does not deliver the thing you actually asked for — "live backdrop blur without forcing users to restructure their app tree."* On every API level below 37.2, the only public-API way to get the backdrop pixels is to re-record a content subtree that **excludes** the overlay, which means users must wrap their blurred content in a target and keep the overlay outside it — and it fundamentally cannot blur across a React Native `<Modal>` (separate window), which is one of the most common places people want a blur (drawers, bottom sheets). So for the flagship use case, this approach is either a restructure or a non-starter, and the only zero-restructure answer (`setBackdropRenderEffect`) has ~0% install base until well into 2027+ and even then measured *slower* on CPU than the re-record path. In other words: **the clean, no-restructure, live, in-window backdrop blur you want is genuinely not achievable on the current Android install base with public APIs. That is a real limitation of the platform, not of your implementation.**

## Proof-of-concept plan

**Build first (smallest thing that proves or kills the approach):**
1. A minimal native `BlurTargetView` + `BackdropBlurView` pair (pure Android, no RN yet): `BlurTargetView` records its subtree into a `RenderNode` each frame it's dirtied; `BackdropBlurView` draws that RenderNode with `setRenderEffect(createBlurEffect(r, r, CLAMP))` at 0.5 input scale, positioned/clipped to a ~400dp panel.
2. Put a fast-scrolling `RecyclerView` (proxy for FlatList) behind it. This isolates the graphics cost from Fabric.
3. Wire the same into a Fabric `HostComponent` and repeat behind a real `FlatList`, to capture RN-specific overhead.

**The measurement that would falsify it:** Run Macrobenchmark capturing **frame overrun / P90 frame duration** during a continuous fling of the list behind the panel, on a **mid-range device (e.g. Pixel 6a / Pixel 8a) at both 60Hz and 120Hz**, release build.
- **Pass:** P90 frame duration stays under budget (≤16.6 ms @ 60Hz; ≤8.3 ms @ 120Hz) with zero/near-zero missed deadlines, at a visually acceptable blur radius (~20–30px effective) and panel size, with downscale 0.5.
- **Falsify:** if P90 exceeds budget or deadlines are consistently missed at 120Hz on mid-range hardware even after downscaling to 0.25 and dropping quality — then the honest conclusion is that live per-frame blur of a large panel isn't sustainable on that hardware and you must fall back to temporal decoupling (re-blur at 15–20fps) or a static blur while scrolling. (Dimezis exhibited a "frozen blur while scrolling on API 31" bug historically — issue #77 / fixed in v3.2.0 — showing even the reference impl hits this wall.)

**Evaluating your seed ideas against the six constraints:**
- **Temporal decoupling (re-blur at 15–20fps):** Survives all constraints; genuinely useful when the *panel* is static and only the backdrop moves — the eye tolerates a slightly stale blur far more than a stuttering one. Recommend as the primary knob when full-rate fails. Caveat: visible lag if the backdrop has sharp high-contrast motion.
- **Scroll-delta reuse (shift cached blurred bitmap by scroll delta, blur only the newly exposed strip):** Clever and constraint-compliant, but fragile: it assumes pure vertical translation with no parallax, no item-appearance animations, no horizontal content, and correct handling of the blur kernel's spatial spread at the seam. High implementation risk for a general library; only worth it if profiling shows capture (not blur) is the bottleneck, which the evidence says it usually isn't (capture is near-free on RenderThread). **Reject for v1; revisit only if measurements demand it.**
- **Aggressive downscale (1/8):** Survives constraints; strongly supported by Haze's measured 5–20% win at 0.5. Quality breaks when the downscale makes text/edges behind the panel resample into mush at low radii, or introduces shimmer during scroll (temporal aliasing) — typically noticeable past ~1/4 for small radii; large radii hide it. Recommend 0.5 default, expose as a prop.
- **Hybrid system-window blur when full-screen + cross-window enabled:** Survives constraints and is a genuine free win in that specific case; recommend as an opt-in mode, not the default (it changes windowing and can't be the general in-window answer).

**One additional non-obvious combination that survives the constraints:** **Change-detection gating + downscale, decoupled from a fixed re-blur cadence.** Combine (a) Dimezis-style "only recapture when the target subtree actually draws" with (b) a *capped* re-blur cadence (e.g. max 30fps) and (c) 0.5 downscale. When the backdrop is static (panel open over a still screen) you pay ~nothing; when it scrolls you pay a bounded, downscaled cost at a cadence you control. This gives you the best headroom on mid-range hardware while remaining 100% public-API and permission-free, and it degrades smoothly into the pure-snapshot floor below API 31.

## Caveats
- **Install-base timing is the whole ballgame.** `setBackdropRenderEffect` is the only clean answer and it's SDK 37.2 (Android 17 QPR2), targeted stable ~December 2026, so effectively 0% today and small for a year+. Everything shippable now is the re-record compromise. (Android 17 stable = June 16, 2026, API 37; QPR2 dates are Google-targeted, not yet officially dated as stable — treat December 2026 as an estimate.)
- **SurfaceView-backed content (video/camera/maps) cannot be captured** by any of the re-record techniques — accept, as you noted. (Haze docs concur: "a SurfaceView cannot be captured.")
- **RN Modal boundary is a hard wall.** A blur inside a `<Modal>` renders in a separate Android window and cannot read the window behind it — no public API fixes this. Document it loudly.
- **The RN-specific per-frame cost is genuinely unmeasured in public.** All hard numbers here are Compose (Haze) or engine (Flutter) benchmarks; your Fabric integration must be measured on-device before you make 60/120fps promises. The exact per-scenario Haze ms cells (Scaffold, Images List, enabled vs disabled) could not be scraped from Haze's benchmark-results page and remain unverified.
- **Benchmark numbers are device- and workload-specific** and mostly CPU-frame-time (which does not capture GPU shader time). Haze itself repeatedly cautions its figures are "useful reference points, not guaranteed savings."
- **The `huanli233.blurview` Maven Central artifact** is convenient but unofficial and lagging; if you want to avoid JitPack, safer to vendor your own Apache-2.0 implementation studying Dimezis/Haze rather than depend on a re-publish.
- **`SDK_INT_FULL` gotcha:** to detect 37.2 correctly, check `Build.VERSION.SDK_INT_FULL >= 3_700_002` (Robolectric 4.17 currently reports 3_700_000 while exposing the API — a known inconsistency reported by chrisbanes, issue #11510).
